# ADR-0013: AMD AMF и Intel QSV (oneVPL) — свои привязки, динамическая загрузка

Статус: принято (2026-10-30). Код на оборудовании AMD и Intel ещё не проверялся (см. «Последствия»).

## Контекст

ТЗ §9.1: аппаратные энкодеры AMF (`amfrt64.dll`, заголовки AMF — MIT) и Intel QSV (oneVPL,
диспетчер — MIT), вход — D3D11-текстура; автовыбор NVENC → AMF → QSV → MF → программный.
Энкодер, недоступный на системе, сообщает причину. Число сессий ограничено драйвером, ошибку
создания сессии нужно показать понятно. На машине разработки — GPU NVIDIA, встроенная графика
Intel (UHD 770) выключена, GPU AMD нет.

## Решение

**AMF** (`cs-encode/src/amf.rs`): `amfrt64.dll` загружается динамически (`AMFQueryVersion`,
`AMFInit` с версией не новее заголовков 1.4.36). Интерфейсы AMF — таблицы методов из C-раздела
заголовков SDK; объявлены только используемые методы (фабрика, контекст, компонент, данные,
буфер), остальные места заняты заглушками того же размера. Места методов проверяются тестом
(`vtable_slots_match_headers`), раскладка `AMFVariantStruct` — `const`-утверждением и тестом.
Контекст инициализируется нашим D3D11-устройством (`InitDX11`), кадр оборачивается
`CreateSurfaceFromDX11Native` — без копий. Энкодер держит не больше `pipeline_depth` кадров
(B-кадры + 4): иначе конвертер перезаписал бы текстуру, которую энкодер ещё читает.

**QSV** (`cs-encode/src/qsv`): диспетчер `libvpl.dll` (MIT; его ставит драйвер Intel вместе со
средой выполнения `libmfx64-gen.dll` / `libmfxhw64.dll`) загружается динамически. Привязки к
структурам сгенерированы `bindgen` из заголовков oneVPL 2.15 (как у NVENC, ADR-0011); сигнатуры
16 функций — вручную. Сессия: фильтр «аппаратная, D3D11», реализация выбирается по LUID адаптера
нашего устройства (`MFX_IMPLCAPS_DEVICE_ID_EXTENDED`; у старых сред выполнения — первая подходящая).
Энкодеру нужны размеры, кратные 16, поэтому кадр копируется **на GPU** (`CopySubresourceRegion`)
в собственный пул выровненных NV12-текстур — как в OBS. К CPU кадр не попадает, требование
«GPU→CPU копий = 0» (§4) выполняется. Пул описан внешним распределителем (`GetHDL`: MemId →
текстура); внутренние кадры библиотека заводит сама (наш `Alloc` отвечает `MFX_ERR_UNSUPPORTED`).

**Общее:**
- Энкодер работает только на GPU своего производителя (PCI-код адаптера: 0x1002 / 0x8086); на
  чужом сразу «недоступен» с причиной. Работа энкодера на одном GPU, когда сцена рисуется на другом,
  не поддерживается: для этого нужна межадаптерная копия.
- `EncoderOptions` (бывшие `NvencOptions`) — общие параметры: пресет P1–P7 (AMF: скорость /
  баланс / качество; QSV: TargetUsage 7…1), профиль, низкая задержка, анализ наперёд (AMF —
  предварительный анализ; у QSV пока не используется), B-кадры.
- B-кадры не опорные; время декодирования — время подачи кадров со сдвигом в кадр, как у NVENC.
  Если GPU не принял B-кадры, кодирование идёт без них.
- SPS/PPS перед каждым ключевым кадром (AMF — `HeaderInsertionSpacing`, QSV — каждый I-кадр IDR).
- Автовыбор: NVENC → AMF → QSV → Media Foundation; выбранный, но недоступный энкодер заменяется
  Media Foundation с записью в журнал.
- `GpuDevice::on_vendor` создаёт устройство на адаптере заданного производителя — для проверки
  энкодера на втором GPU (тест `vendor_gpu`).

Перегенерация привязок oneVPL (нужны `libclang` и `bindgen-cli`; `wrap.h` подключает
`vpl/mfxvideo.h` и `vpl/mfxdispatcher.h` из `api/` репозитория intel/libvpl, тег v2.15.0):

```
bindgen wrap.h -o sys.rs --allowlist-type 'mfxVideoParam|mfxFrameSurface1|mfxBitstream|mfxFrameAllocator|mfxFrameAllocRequest|mfxFrameAllocResponse|mfxHDLPair|mfxEncodeCtrl|mfxSyncPoint|mfxSession|mfxLoader|mfxConfig|mfxVariant|mfxExtCodingOption|mfxExtCodingOption2|mfxExtCodingOption3|mfxExtendedDeviceId|mfxStatus|mfxIMPL|mfxVersion|mfxHandleType|mfxImplCapsDeliveryFormat|mfxExtVideoSignalInfo|mfxHDL|mfxMemId|mfxAccelerationMode|mfxImplType'   --allowlist-var 'MFX_.*' --default-enum-style consts --no-prepend-enum-name --no-doc-comments --use-core   -- --target=x86_64-pc-windows-msvc -I.
```

## Альтернативы

- Только аппаратные MFT Media Foundation (уже есть, у AMD и Intel они тоже есть): нет пресетов,
  управления B-кадрами и предварительным анализом, качество и стабильность MFT у разных драйверов
  разные. Остаются запасным путём.
- Крейты-обёртки AMF/oneVPL: нет поддерживаемых с D3D11-входом без статической компоновки.
- `bindgen` для AMF: заголовки — C++ с C-разделом под макросами; ручные таблицы нужны лишь для
  пяти интерфейсов, их места проверяются тестом.
- Статическая сборка диспетчера oneVPL из исходников: лишняя C++-сборка; диспетчер ставится
  драйвером Intel.
- Новый путь oneVPL 2.10+ (`MFXMemory_ImportFrameSurface`) без распределителя: поддерживается
  только новыми средами выполнения (Gen12+), распределитель работает и со старыми.

## Последствия

- На машине разработки проверено: сборка, модульные тесты (места методов AMF, раскладка
  параметров QSV), отказ с причиной без GPU AMD/Intel, автовыбор NVENC. Кодирование на реальных
  GPU AMD и Intel не проверялось: тест `cargo test -p cs-encode --test vendor_gpu -- --ignored`
  нужно прогнать на таких машинах (на машине разработки — после включения встроенной графики
  Intel в BIOS). До проверки ошибка на этапе открытия даёт переход на Media Foundation, а ошибка
  в работающем энкодере останавливает запись с сообщением.
- Пробное кодирование 10 кадров при запуске (2.9, `cs-encode/src/probe.rs`) отсеивает энкодер,
  который открывается, но не работает: рабочим считается тот, что выдал по пакету на кадр без
  отброшенных кадров, первый — ключевой с SPS/PPS. «Авто» берёт первый рабочий по цепочке, не
  прошедшие пробу в списке настроек неактивны с причиной.
